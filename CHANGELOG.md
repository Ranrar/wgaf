## [Unreleased]

### Added

- **`tests/apps/` — GTK4 applications that wgaf drives in its own tests and that report what they actually received.** Tests have so far driven `gtk4-demo`, an application this project does not control: their expectations are facts discovered by hand-scanning its widget tree, which a GTK upgrade can invalidate silently, and they cannot run anywhere it is not installed — which is exactly how CI broke. These applications draw a fixed, known UI, so a failure means wgaf changed rather than the toolkit did.

  The rule they exist to enforce is that **an assertion never travels back through the code path under test**: `wgaf type "hello"` is verified by reading the application's own report, never by asking `wgaf a11y info` what the application contains, since one bug in the accessibility layer would otherwise produce a false pass and blame the wrong subsystem. The shared `report` crate is that channel — a JSON file rewritten in full on every observed change, carrying a monotonic `seq` so a test can tell "not started" from "started, nothing has happened" from "a new event arrived". Each report is written to a sibling temporary file and `rename(2)`d into place, so a polling reader sees the previous report or the new one and never a torn document; that property is asserted by a test with a concurrent reader, and verified by mutation — writing in place fails it.

  They are a **separate Cargo workspace with their own lockfile**, excluded from the root one, so `cargo build` and `cargo test` still need no GTK4 development packages. Only `make test-apps` does.

  Second application is `input-test`: one window with a text entry and a button, reporting every key, click, pointer motion and scroll it receives. This closes the readback gap that `tests/input.rs` leaves open — that suite proves synthesized events reach the *kernel*, and between the kernel and an application sit libinput, the compositor, the xkb keymap and the toolkit, none of which it can see past. It found a real one on its first run: `wgaf type` had been pressing the wrong key for almost every letter (see Fixed).

  Its report deliberately carries **both** the entry's text and the raw key events with their modifier state, because they fail differently. The text is the honest end-to-end answer but depends on the session's keyboard layout, since wgaf synthesizes US-QWERTY key *positions*; the raw events arrive whatever the layout is. So an empty event log means the input never arrived, while a populated log with unexpected text means it arrived and the layout translated it — different bugs, and only one of them wgaf's. This is also what makes the shift path checkable at last: `wgaf type` synthesizes `KEY_LEFTSHIFT` around capitals and shifted symbols, and nothing had ever verified the result.

  Controllers are attached to the window rather than to a child widget, in the capture phase, which was learned by running it: a key event only reaches widgets on the path to the focused one, so a controller on the content box observed nothing at all when no widget held focus — the state a freshly mapped window is in unless the focus widget is set before it is presented. Clicks are captured window-wide for a different reason: absolute pointer positioning does not exist yet, so a test cannot aim at a small widget, and a target the size of the window is the only one it can reliably hit.

  First application is `window-test`: three windows — a main window with a header bar, an independent second top-level, and a dialog transient for the main one, since multi-window applications are where enumeration realistically breaks — reporting each one's title, size, focus, and visibility. Two limits are documented rather than worked around, because both are properties of Wayland rather than gaps to fill. **A window's position is not reportable**: a Wayland client is never told where the compositor placed it, so `wgaf window move` cannot be checked against the application's own account of itself, and the only other source is the extension's own reply — which would be verifying wgaf with wgaf. **Which window holds focus at startup is not deterministic**: three identical runs gave focus to three different windows, so tests must assert the change `wgaf window focus` causes rather than the state preceding it.

- **A rate limit on synthesized input**, configured by `input_max_events_per_second` in `config.toml` (default 3000, `0` disables it). The failure it exists for is a script with a loop bug: synthetic input floods the desktop, and the user cannot regain control because their own keystrokes compete with the flood. Until now the only guard was `TypeText`'s 4096-character cap, which is a weaker protection than it looks — that is roughly 16,000 kernel events, and nothing stopped a caller issuing that call in a loop.

  **This is a safety guard, not a security control**, and the distinction decided the design. `org.wgaf.Input1` is on the session bus, and any process running as this user can open `/dev/uinput` directly — that is what the documented udev-rule/`input`-group setup grants, to the account rather than to wgaf. A limit that a hostile local process bypasses by talking to the kernel itself protects nobody, so this lives in `config.toml` as an engineering ceiling rather than in `permissions.toml` as policy, and next to `MAX_TYPE_TEXT_LEN` in `input/mod.rs` rather than in the permission gate — which covers window operations too, where rate limiting is meaningless.

  Exceeding the budget **slows a call down rather than failing it**, so a legitimate long-running automation still completes, with one `tracing` warning per run so a throttled user learns why things got slow instead of guessing. Only when the backlog would exceed 30 seconds does a call fail, with a new named D-Bus error `org.wgaf.Input1.Error.RateLimited` (exported as `wgaf_common::INPUT_ERROR_RATE_LIMITED` and drift-asserted like the other four) — that state means a runaway rather than a busy caller, and a refused call is deliberately not charged, so one runaway does not cascade into refusals for the calls behind it.

  The budget counts **kernel events, not calls**: a maximum-length all-capitals `TypeText` is 16,384 events (press plus release, doubled again for the `KEY_LEFTSHIFT` around each capital) where a `KeyPress` is one, so calls are not comparable units. One global bucket, deliberately not keyed by caller — there is one pointer and one keyboard focus, and per-caller buckets would let N processes multiply the ceiling exactly when the guard matters most. Tokens are allowed to go negative so that a single call costing more than the entire bucket waits for its debt rather than deadlocking against a capacity that can never cover it.

  Checked in `InputBackend::run`, already the sole funnel every synthesized event passes through, and before the `uinput` device is resolved — so a refused call never creates the device. The bucket arithmetic takes the current instant as an argument and neither reads a clock nor sleeps, which lets it be unit-tested with an injected clock; a wall-clock test of a rate limiter is a flaky test. Default chosen by reasoning about orders of magnitude (a fast typist produces ~40 events/second) and **not yet measured against the point at which GNOME Shell stops keeping up** — it should be tuned against a real session.

  This is a mitigation, not a fix. The complete answer to a runaway script is a kill switch, which remains unbuilt.

- **`TypeText`'s character cap is now configurable**, as `input_max_type_text_chars` in `config.toml`, defaulting to the 4096 it was previously hardcoded to. Lowering it means an oversized paste is refused outright rather than typed into whichever window happens to be focused — worth having against accidents and opportunistic pastes, and cheap for a user who never types more than a line at a time.

  The cap survives the arrival of the rate limiter rather than being subsumed by it, because it bounds a different axis: **the limiter paces between calls, not within one.** It charges a call's whole cost up front, sleeps once, and then emits every event as fast as the kernel accepts them, so this cap is the only bound on how much a single call can fire uninterruptibly.

  Stated plainly in the user guide and the config template, because it would otherwise be easy to over-trust: **this is not a security control.** A caller that can issue one `TypeText` can issue a hundred, and any process running as this user can open `/dev/uinput` directly without involving wgaf. What it buys is that a mistake fails loudly.

  `TextTooLong` also became a **named** D-Bus error, `org.wgaf.Input1.Error.TextTooLong` (`wgaf_common::INPUT_ERROR_TEXT_TOO_LONG`). It had been flattened into a generic `zbus::Error::Failure` since Phase 4, which was defensible while the cap was a fixed 4096 only runaways hit — but a user-chosen limit makes it an ordinary outcome, and a script should be able to branch on "too long" without string-matching a description.

  **`0` means no characters may be typed, not "unlimited"** — deliberately the opposite of `input_max_events_per_second`'s `0`. Reading it as "unlimited" would hand an uncapped paste to whoever typed `0` intending to switch the guard off, which is the one outcome the setting exists to prevent; the inconsistency is called out in both the template and the guide. `TextTooLong` now names the configured limit rather than a compiled-in constant, so a user who set 256 is not told about 4096, and names the setting to change. The check runs before the rate limiter and before the device is resolved, so an over-length call waits for nothing, spends no budget, and registers no `uinput` device.

- `wgaf status` and the `org.wgaf.Daemon1.Status` method behind it — a single command answering "is this set up correctly?". It reports whether the GNOME Shell Extension bridge, `/dev/uinput`, and the AT-SPI accessibility bus are each usable right now, carrying the daemon's own actionable guidance for whichever is not, plus daemon version/pid/uptime and the effective permission policy. Until now those three failure modes were discoverable only by triggering them: a user had to guess which subsystem to poke and interpret an error from a command they did not actually want to run. It also closes a real gap in shipped Phase 6 behaviour — a caller refused by `permissions.toml` had no way to see which file the refusal came from or what else was restricted, and the path may be an XDG default they never chose explicitly. This is the transparency mechanism the roadmap's security model called for and which had never been built.

  `make install` now also installs `~/.config/wgaf/config.toml` and `permissions.toml` from templates in `packaging/`, never overwriting an existing file. The templates state every setting and every capability explicitly, at the values the daemon applies when they are absent, so a freshly installed pair behaves exactly as if neither file existed while showing the whole configurable surface rather than hiding it behind comments. The tradeoff, stated at the top of both files, is that written values are pinned: a later version that changes a built-in default will not reach anyone who has run `make install` unless they comment the line out. `wgaf status` reports each file's resolved location whether or not it exists, marking absent ones, so users who install via `cargo install` (and so never run `make install`) still learn where the files go.

  Deliberately ungated, with no `Capability` variant: a transparency mechanism that policy could switch off would defeat its own purpose, and it exposes nothing a caller could not already learn by attempting the operations it describes. It is also side-effect free — probing `/dev/uinput` opens and immediately closes it without issuing any ioctl, so a status query never registers a virtual input device (guarded by a test), and the extension and accessibility probes deliberately bypass their availability caches, which store success permanently and would otherwise report a subsystem as healthy long after it stopped being so. Exits non-zero when any subsystem is unavailable, so it can gate a setup script. Only the `--json` shape is a stable interface.

- `org.wgaf.Accessibility1.Error.InvalidElementRef` — a named D-Bus error for an element reference that is not a well-formed `(bus name, object path)` pair, exported as `wgaf_common::ACCESSIBILITY_ERROR_INVALID_ELEMENT_REF` and drift-asserted like the other four. Previously `wgaf a11y info 'nosuch#/x'` escaped as a bare `zbus::Error`, which the API layer flattened into a generic failure. Kept deliberately distinct from `ElementNotFound`, because the remedies differ: a *malformed* reference is a caller mistake to fix at the call site, while a *stale* one was valid when issued and simply needs re-querying — collapsing them would tell users to re-run a query that was never going to help. The message names the offending reference and gives the expected form.

- `wgaf-cli`: five regression tests over the error-rendering decision, which nothing previously asserted on. One guards the whole named-error table at once against the stuttering regression rather than testing a single arm.

- `wgaf-daemon`: a drift test pinning `windows/proxy.rs` against the GNOME Shell Extension's actual D-Bus contract. The proxy previously asserted only the bus name, object path, and interface name — a method or signal whose *signature* diverged from `extension/dbusInterface.js` was caught by nothing, because `zbus` resolves proxy calls at runtime and the extension is a separate GJS program the compiler never sees. Such a divergence surfaced as a raw `UnknownMethod` on a user's desktop, at the moment they ran the command. The test now reads the extension source with `include_str!`, resolves its `${...}` template interpolations from the JS constants, parses `DBUS_INTERFACE_XML`, and asserts every method and signal matches — plus that the extension's own bus name, object path, interface name, and `WindowNotFound` error name equal the `wgaf_common` constants the daemon dials, which nothing checked from the extension side before. Verified by mutation: a changed argument type, an added method, a changed signal payload, and a `V1`→`V2` rename each fail it. Argument types are named as Rust types (`sig::<u32>()`) rather than signature strings, so a wire-format change to `WindowRecordDict` flows through on its own. Done now rather than alongside the work that needs it: absolute pointer positioning and window-signal subscription both grow this interface, and the test is worth having before there is anything to catch. No new dependency — the XML subset the extension emits is scanned in about forty lines rather than pulling in an XML crate.

- `.github/workflows/ci.yml` — continuous integration, which this project had none of. Three jobs: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and the test suite. Formatting is its own job so a formatting nit reports as one rather than hiding behind a compile error; the whole workspace was reformatted in the same change, since the check fails against the tree as it stood and `cargo fmt` was until now a trap that produced a large unrelated diff for anyone who ran it.

  The test job is split by what each group actually needs, which was measured rather than assumed. Unit tests need nothing (verified with no session bus present). The integration tests for `ping`, `default_config_path`, `windows_stub`, `permissions`, and `status` need a session bus and nothing else, so they run under `dbus-run-session`, which creates a private one per invocation — this also makes them independent of whatever state the host bus is in. `input` and `accessibility` need a writable `/dev/uinput` and a live AT-SPI bus with `gtk4-demo` present, which no hosted runner has; they are gated to local [`act`](https://github.com/nektos/act) runs via the `ACT` variable act sets, with the required `--container-options` invocation documented in the workflow header. Deliberately not `continue-on-error`, which would turn a real regression into silence.

### Changed

- `README.md` gains a **"Known issues"** section, noting in one line each that synthesized input goes to whatever holds keyboard focus rather than to a window you name, and that `wgaf type` assumes a US keyboard layout. Both are long-standing behaviours that had no single place a user would find them. `README.md` and `packaging/config.toml` also describe the new device settle time.

  **wgaf does not defend against input reaching the wrong window, and that is a decision for 1.0 rather than an omission.** Input cannot be aimed at a window — Wayland gives no client a way to direct input at another, which is a restriction this project respects rather than routes around. The available guard is refusing to synthesize when the intended window is not focused; it is designed but not built, because it carries open questions (opt-in or mandatory, whether a long `TypeText` re-checks mid-burst) that the release is not being held for.

- User-facing documentation updated for the two new input limits: `README.md` gains an "Input safety limits" section, lists them in the `config.toml` summary, and notes that the defaults are generous enough that neither is met by accident; `docs/user-guide.md` explains both, including why `0` means opposite things for the two settings, and states that they are safety nets rather than security controls; `docs/cli-reference.md` documents the cap under `wgaf type` and adds `text too long` and `input rate limit exceeded` to its error list, noting that merely exceeding the speed limit produces no error at all.

- `wgaf-cli` now recognizes every named D-Bus error the daemon can send, enforced by a drift test rather than by memory. The CLI's error-name table is what turns a reply into a readable sentence when the reply carries no description, and `INPUT_ERROR_RATE_LIMITED` had been added to `wgaf-common`, mapped in the daemon, and drift-asserted daemon-side while never reaching that table — a description-less reply would have printed the raw dotted error name at a user, with nothing failing. The new test scans `wgaf-common`'s source for `*_ERROR_*` constants and asserts each is recognized, so a future error fails the build until the CLI decides what to call it. The extension's own error names are excluded deliberately: they are translated daemon-inward and never reach a CLI client. Verified by mutation in both directions — removing a table arm and adding an unrecognized constant each fail it. The scan also pins the expected constant count, which caught the first version of the test silently skipping the six constants whose declarations wrap onto a second line.

- `packaging/config.toml` and `packaging/permissions.toml` now state every setting and every capability at its default value, instead of shipping with everything commented out. The whole configurable surface is visible and editable in place rather than something users have to uncomment to discover. Behaviour is unchanged — verified: the daemon reports `no capability restricted — every capability allowed`, identical to the previous empty `[capabilities]` table. The tradeoff is that written values are pinned, so a later version changing a built-in default will not reach anyone who has run `make install` unless they comment the line out.

  Both files were also cut back to a one-line header pointing at `README.md`, and the `config-install` recipe's comments in the `Makefile` with them. They had accumulated explanations of install paths, file modes, the `Allow`/`Deny`/`Prompt` values, and which operations can be gated — all of which `README.md` already covers, in more depth and where users actually look.

### Security

- **`config.toml` and `permissions.toml` must both be present for the daemon to start**, so that the settings and policy it runs under are always the ones visible on disk rather than an implicit fallback. Empty files select the defaults explicitly — an empty `config.toml`, and a `permissions.toml` containing an empty `[capabilities]` table. `--config-optional` and `--permissions-optional` run without the respective file. Default-allow still applies *within* a policy file — an unlisted capability is allowed — so this is not a switch to default-deny.
- **Both files must be owned by the user the daemon runs as (or root), and must not be group- or world-writable**, on the same reasoning `ssh` applies to private keys. The daemon reports the offending mode and the exact `chmod`/`chown` to fix it. Shared validation lives in `wgaf-daemon/src/secure_file.rs` so the rules for the two files cannot drift apart. `make install` sets mode `600` on both, since `cp` honours the umask (002 on many distros, yielding a group-writable 0664).

### Fixed

- **The first input command after the daemon started was silently discarded.** `wgaf type` reported typing 34 characters and the application received nothing; running the same command again worked. Creating a `uinput` device does not make it usable — `UI_DEV_CREATE` returns as soon as the kernel has the device, but udev has still to publish it and the compositor has still to open it through libinput, and events written before that are accepted by the kernel and delivered to no one. The daemon had no way to notice, so it reported success.

  The daemon now waits after creating the device, configurable as `input_device_settle_ms` in `config.toml` and defaulting to 300 ms. The cost is paid **once per daemon lifetime**, not per command, because the device is created at most once.

  The delay was measured rather than guessed: `udevadm monitor` puts udev's processing of the new event node 36 ms after the kernel's own `add`, and the empirical threshold agrees — a 0 ms wait loses every event, 50 ms delivers all of them. The default sits an order of magnitude above that, since being slow once is cheap and being wrong is silent.

  **This is a stopgap, and a duration is the wrong shape for it.** It was chosen on the belief that the last hop — the compositor opening the device — could not be observed from the daemon's process. That turned out to be wrong: the compositor holds the device's own event node open, under the same user the daemon runs as, so waiting for the real condition rather than for a clock is possible and is what should replace this. Until then the wait is generous and the setting exists so a slow machine can raise it.

  Found by `tests/apps/input-test`, and not findable without it: `tests/input.rs` reads synthesized events back from the kernel, which is the one place they did arrive.

- **The test suite no longer types into the developer's focused window.** `wgaf-daemon/tests/input.rs` and `tests/permissions.rs` synthesize real keystrokes through a real kernel device and have no window of their own to aim at, so between them a run sent 4096 `a` characters (with the rate limiter deliberately off), `ab1!`, and `hi` to whatever happened to be focused. This was latent until the settle fix above: every one of those payloads was its test daemon's *first* input command, so the whole suite had been injecting into the void, and the two defects concealed each other — the suite looked harmless because it was broken. Both suites now set `input_device_settle_ms = 0` for their spawned daemons, restoring non-delivery deliberately, with the reasoning recorded at the call site. It is a mitigation and not a guarantee; running the suite against a nested compositor is the real fix.

- **`wgaf type` and `wgaf key press` pressed the wrong key for 25 of the 26 letters.** `wgaf type "Hello, World!"` produced `Kg½½z, :zv½f!`; `wgaf key press d` pressed `f`. Only `a` was correct. Both commands resolved a letter by adding an alphabetical offset to `KEY_A`, but evdev numbers the letter keys by their **position on the physical keyboard**, row by row — `q w e r t y u i o p`, then `a s d f g h j k l`, then `z x c v b n m` — so the codes are alphabetical nowhere and the error grew with distance from `a`. For `y` and `z` the arithmetic ran off the end of the letters entirely and pressed `KEY_RIGHTSHIFT` and the keypad asterisk. Letters now come from an explicit table, in both places that resolve one.

  The defect had been present since keyboard synthesis shipped, and the existing tests could not have caught it: `tests/input.rs` reads the synthesized events back from the kernel and compares them against the same table that produced them, so it confirmed wgaf was consistent with itself. What exposed it was the first end-to-end run of `tests/apps/input-test` — an application reporting the characters it actually received, which is precisely the readback gap that application was built to close. Four regression tests now pin the mapping against the literal values in `<linux/input-event-codes.h>` rather than against this project's own constants, assert that `wgaf key press <letter>` and `wgaf type <letter>` agree, and assert that no letter maps onto a modifier or a keypad key.

- `wgaf status` no longer prints a Rust `Debug` dump when the accessibility bus is unreachable, and no longer guesses at the cause. It reported `AT-SPI accessibility bus unavailable: ZBus Error: InputOutput(Os { code: 2, kind: NotFound, message: "No such file or directory" }) — accessibility may not be enabled for this session`, which buried the one actionable fact (a socket does not exist) in type syntax and then closed with a hint that was simply wrong in the case that produced it — accessibility *was* enabled; its bus had exited and `org.a11y.Bus` was still handing out the dead address.

  The `Debug` text could not be fixed where it appeared. The `atspi` crate formats any underlying `zbus::Error` with `{:?}` into a `String` at conversion time, so by the time wgaf sees the error the original is gone and there is nothing left to render with `Display`. That error is now kept for the daemon's debug log only, and the user-facing message comes from a diagnosis of wgaf's own: on failure it repeats the two steps the connection takes — reach the session bus, ask `org.a11y.Bus` for the accessibility bus address — and reports which one broke. A missing service says accessibility is not available for the session and names the package providing it; an address whose socket does not exist says the address is stale and that logging out restores it; anything else points at `--log-level debug` rather than inventing a cause. The trailing hint is gone from the error type entirely, because it was appended to every failure on the path regardless of which one occurred.

  Verified against both live cases on an isolated D-Bus session, and the wording is pinned by unit tests — including one asserting no branch can emit Rust type syntax, which is the defect class itself rather than this one instance of it.

- `wgaf-daemon`: startup errors were printed with `Debug` rather than `Display`, for the same reason the CLI's were — returning `Result` from `main` uses Rust's `Termination` impl. A policy-file problem printed `Missing { path: "..." }` instead of the multi-line guidance it carries. The daemon now prints `error: <message>` to stderr and exits 1.
- `docs/cli-reference.md`: documented that `wgaf mouse move` is **not** pixel-exact — `libinput` applies pointer acceleration to relative motion, so the pointer does not land exactly `dx`/`dy` pixels away. True of the behaviour since Phase 4 and stated nowhere until now, which made it easy to assume a 1:1 mapping that has never existed. Also documented the daemon's configuration-file lookup (`$XDG_CONFIG_HOME/wgaf/config.toml` with a `~/.config` fallback, `permissions.toml` as its sibling) in the CLI reference and user guide, which previously covered only the README.
- `wgaf-cli`: errors are no longer printed via `Debug`. Returning `Result` from `main` means Rust's `Termination` impl formats with `Debug`, not `Display` — which wrapped every message in quotes (`Error: "unknown key ..."`) and printed raw struct internals for anything that wasn't a plain string. A mistyped element reference produced `MethodError(OwnedErrorName("..."), Some("..."), Msg { type: Error, serial: 61, sender: UniqueName(":1.5042"), body: Str, fds: [] })` — D-Bus serials and fd lists shown to a user whose actual mistake was a typo. `main` now prints `error: <message>` to stderr and exits 1.
- `wgaf-cli`: named errors are no longer double-prefixed. The CLI prepended its own label to a daemon message that already opened with the same words, so `wgaf key press notakey` printed `"unknown key: unknown key \`notakey\`"`. Systemic across roughly six error arms, including the extension-unavailable and device-unavailable messages that are the two most likely things a new user sees — and the ones carrying the actionable setup instructions, where stuttering reads as a bug in wgaf at exactly the wrong moment. The daemon's `#[error(...)]` text is now the single source of truth; the CLI's label survives only as a fallback for a reply that carries no description at all.

### Changed

- `wgaf-cli`: `connect()` and `map_err` were byte-identical triplicates across `commands/{window,input,accessibility}.rs`, differing only in a doc comment naming each interface's error set. Both now live once in `commands/mod.rs` alongside `describe_dbus_error`. `ping` was switched onto the shared pair too — it called `Connection::session()` directly and propagated raw errors, making it the one command that could still surface an unrendered failure.
- `wgaf-cli`: added `wgaf-cli/src/output.rs` as the single place defining what `--json` emits. `print_ok` was previously duplicated verbatim in `commands/window.rs`, `commands/input.rs`, and `commands/accessibility.rs`, with `commands::ping` carrying a fourth inline variant, and the pretty-printed record arm (`serde_json::to_string_pretty`) repeated at six call sites. The JSON these produce is a machine-readable interface, so it needs one definition that changes deliberately rather than four that can drift. Pure refactor — every output shape is byte-identical, including `ping`'s divergent `{"ok": true, "response": ...}` key, which is preserved as-is and documented as a wart to resolve when the JSON contract is next versioned deliberately.

## [0.7.0] - 2026-07-28

### Added

- `wgaf-daemon`: regression tests for the `Prompt` permission flow (`wgaf-daemon/src/permissions/notify.rs`'s own `mod tests`, 3 tests) — an Allow click resolving to permission granted, and a Deny click and a dismissal-without-a-button-press both resolving to refusal (the fail-closed contract, previously untested). They run against a stub `org.freedesktop.Notifications` service on a private, unique bus name on the session bus, the same pattern `wgaf-daemon/tests/windows_stub.rs` uses for the GNOME Shell Extension; the real notification bus name is owned by GNOME Shell on a live session and cannot be faked. The stub emits its response signal *before* replying to `Notify`, which is what makes the tests deterministic rather than timing-dependent: under the pre-fix ordering the bus has no match rule to route that signal to and drops it every time. Verified to genuinely catch the regression by temporarily reverting the fix — all three failed in ~5s, bounded by a per-test 5-second timeout rather than the 60-second `PROMPT_TIMEOUT`. These guard the `prompt_user` ordering fix released in 0.7.0, which shipped without test coverage.
- `wgaf-daemon`: `permissions::notify::prompt_user_at` — an internal seam letting the notification service's bus name be overridden for testing, mirroring `Config::extension_bus_name`'s existing role on the `org.wgaf.Windows1` side. `prompt_user` is unchanged for callers and always targets the real `org.freedesktop.Notifications`.

### Changed

- `wgaf-daemon`: the `wgaf-daemon` unit test binary now requires a session bus, which it did not before (the integration tests already did) — the new `permissions::notify` tests deliberately fail rather than skip when no bus is available, since a silently skipped regression test is worse than a failing one. Run the suite under `dbus-run-session -- cargo test` in environments without one.

## [0.7.0] - 2026-07-27

### Fixed

- `wgaf-daemon`: `permissions::notify::prompt_user` (`wgaf-daemon/src/permissions/notify.rs`) subscribed to the `ActionInvoked`/`NotificationClosed` signals *after* posting the notification, leaving a window in which a user's "Allow" click on a `Prompt`-policy capability was dropped entirely — the call then blocked the full 60-second `PROMPT_TIMEOUT` and failed closed, making an instant, deliberate approval indistinguishable from ignoring the prompt. Both signal streams are now subscribed before `Notify` is called, so no response can be missed however quickly it arrives. Found by inspection during the 2026-07-27 documentation audit; no automated test guards the ordering (see the phase 6 notes for the private-bus stub a regression test would need).
